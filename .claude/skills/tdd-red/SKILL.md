## STEP 1 — 인터뷰

이미 파악된 항목은 생략, 불명확한 항목만 질문:

| 항목     | 질문 예시                         |
|--------|-------------------------------|
| 도메인 규칙 | "반드시 지켜야 할 비즈니스 규칙이 있나요?"     |
| 예외 조건  | "어떤 입력·상태에서 실패해야 하나요?"        |
| 상태 전이  | "호출 전/후로 변해야 하는 엔티티 상태가 있나요?" |
| 외부 의존  | "DB, 외부 API 등 외부 의존이 있나요?"    |

인터뷰 마지막에 항상 추가:

> "위 항목과 무관하게, 이 기능에서 반드시 검증돼야 한다고 생각하는 시나리오가 있나요?"

응답이 있으면 STEP 3 필터링 없이 STEP 4 출력에 직접 포함

---

## STEP 2 — 케이스 도출 (내부 수행, 출력 없음)

3가지 방법론을 순서대로 적용해 후보를 최대한 확보:

### 동치 분할

- 유효 입력 그룹 / 무효 입력 그룹을 분리
- 각 그룹에서 대표 케이스 1개씩 도출

### 경계값 분석

- 숫자: 최솟값, 최솟값+1, 최댓값-1, 최댓값
- 컬렉션: 빈 컬렉션, 단일 원소, 다수 원소
- null / 빈 문자열 / 0

### 상태 전이

- 정상 흐름에서의 상태 변화 검증
- 예외 발생 시 상태 롤백 여부
- 동일 메서드 반복 호출 시 멱등성

---

## STEP 3 — 유효성 필터링 (내부 수행, 출력 없음)

각 후보를 아래 기준으로 평가하며 모두 통과한 것만 유지

| 기준      | 검증 질문                                           | 기준 미달 시        |
|---------|-------------------------------------------------|----------------|
| 결함 탐지력  | 이 테스트 없이 잘못된 구현이 빌드를 통과할 수 있는가?                 | 제거             |
| 실패 시나리오 | 실패시키는 입력·상태·호출 순서를 한 줄로 기술할 수 있는가?              | 제거             |
| 구현 독립성  | observable outcome과 business invariant를 검증하는가?  | 외부 동작 기준으로 재작성 |
| 경제성     | 다른 테스트가 동일 behavior를 이미 보호하거나, 더 적은 수로 보호 가능한가? | 병합 또는 제거       |
| 유지보수성   | 리팩터링 시 불필요하게 깨질 가능성이 높은가?                       | 단순화 또는 제거      |
| 명세 연결성  | 보호하는 요구사항·비즈니스 규칙을 즉시 설명 가능한가?                  | 제거             |

추가 규칙:

- 테스트 추가보다 제거 가능성을 먼저 검토
- 하나의 테스트는 하나의 핵심 behavior만 보호
- mock·interactions 검증보다 observable outcome 검증 우선
- trivial getter·setter·runtime behavior 테스트는 생성하지 않음
- setup이 assertion보다 복잡하면 제거를 먼저 검토

## STEP 5 — 테스트 구조 확정

STEP 4 목록을 테스트 클래스·메서드로 매핑

### 테스트 레벨 결정

| 레벨                | 적합한 검증 대상                         |
|-------------------|-----------------------------------|
| 단위                | 비즈니스 로직, 실행 순서, 조건 분기             |
| `@DataJpaTest`    | JPA 영속화, 레포지토리, DB 상태 전이          |
| `@SpringBootTest` | Security 필터, 다수 레이어가 얽혀 분리 불가한 경우 |

`@SpringBootTest`는 최대한 지양, 단위·DataJpaTest로 검증 불가할 때만 사용

### 출력 형식

```markdown
**`{TestClassName}`**

- {단위\|DataJpa\|통합}
    - `{메서드명}`
    - {한 줄 설명}
```

- 클래스가 여러 개면 위 블록을 반복
- 레벨 순서대로 그룹화 (단위 → DataJpa → 통합)
- 사용자 검증 후 테스트 작성

---

## STEP 6 — 테스트 작성

### 코드베이스 탐색 제약

- 코드베이스 탐색은 테스트 작성에 필요한 최소한의 컨텍스트(인터페이스, 컨벤션, 경로) 수집까지만 허용
- 구현 로직 이해를 위한 탐색 금지

### 테스트 작성 규칙

- 메서드: Given-When-Then 패턴
- 메서드 위 한국어 주석으로 한 줄 설명 작성
- 클래스/메서드명: 영어 PascalCase/camelCase

## STEP 7 — FAIL 확인

레벨 순서대로 개별 실행해 FAIL 확인 (단위 → DataJpa → 통합):

```
./gradlew test --tests "*{클래스명}" -q
```

보고:

```
RED 완료. [N]개 테스트 작성, 전체 FAIL 확인
```
