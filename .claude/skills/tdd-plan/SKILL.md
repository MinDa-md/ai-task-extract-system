## STEP 2 — 비즈니스 레벨 인터뷰

확정된 목표를 기준으로 질문-답변 라운드(라운드 당 질문 3개 이하)를 반복함

**질문 선택 기준** (우선순위 순):

1. 이 기능이 완료됐을 때 어떤 동작·결과가 보여야 하는가
2. spec에서 발견한 모호함·모순·누락
3. 스코프 경계 — 이번에 하는 것 vs 명시적으로 제외하는 것
4. 예상 엣지케이스 (장애 상황, 순서 문제, 상태 전이, 동시성 등)

**질문 금지 항목** — 아래는 plan 세션 범위 밖. red/green/refactor 세션에서 agent가 자율 결정:

- 클래스명, 메서드명, 패키지 구조 등 구현 세부사항
- 특정 인터페이스·라이브러리·패턴 등 구현 방법 선택

**종료 조건**: 모두 충족되면 인터뷰 종료. 하나라도 미달이면 라운드를 계속함:

- [ ] 완료 기준이 명확한가
- [ ] 스코프가 명확한가
- [ ] 주요 엣지케이스가 식별됐는가
- [ ] 상태를 갖는 주체를 모두 나열했는가
- [ ] 각 주체가 실행 / 데이터 / 도메인 중 어느 레벨인지 명시했는가
- [ ] 같은 역할을 하는 주체가 두 곳 이상이라면, 둘 다 필요한 이유를 정당화할 수 있는가
- [ ] 도메인 결정 항목(상태 정의, 상태 전이 기준, 개념 경계)이 미결인 채로 남아 있지 않은가

### 도메인 결정 항목 처리 규칙

- 도메인 결정 항목은 사용자에게 제안하고 승인받은 후 구현 계획에 반영
- 미승인 항목은 구현 계획에 미결정으로 명시

## STEP 3 — 구현 계획 작성

### `docs/{feature}/discuss.md`

**ADR 작성 기준** — 다음 조건을 모두 충족하는 경우에만 작성:

- 실제 대안이 두 개 이상 존재했는가
- 여러 컴포넌트에 영향을 미치거나 번복 비용이 큰가
- 나중에 "왜 이렇게 했는가"를 설명할 필요가 생길 수 있는가

**ADR 제외 대상**:

- 구현 세부사항 (클래스명, 메서드 설계, 패키지 구조 등)
- 스코프 결정 (이번에 할 것 vs 제외할 것)
- 합리적인 대안이 없는 자명한 선택

```markdown
## ADR-NNN: {제목}

- 결정: {내용}

- 이유: {내용}

- 기각된 대안: {내용}
```

### `docs/{feature}/plan.md`

```markdown
## 목표

- {핵심 목표 한 줄}
- 필요성: {한 줄}
- 완료 후 변화: {한 줄}

## 구현 범위

- {레이어}: {이 레이어에서 달성해야 할 것}

## 스코프 아웃

- {항목}: {이유}

## 제약

- {규칙}: {이유}

## 엣지케이스

- **{케이스}**: {처리 방향}

## Green condition

- {통과 기준}

## 사용자 명시 사항

- {지시 내용}
```

## STEP 4 — 사용자 검토 및 피드백 처리

- STEP 3 수행 이후 plan 수정 요청은 비판적으로 평가

- 아래 경우 거절하고 근거를 설명:
    - ADR 기각된 대안 채택 (discuss.md 참조)
    - 인터뷰에서 합의한 스코프 외 확장

- 거절이 아닌 경우:
    - Edit 도구로 해당 섹션만 수정(전체 재작성 금지)
    - 수정 후 변경 내용을 한 줄 요약하고 재검토를 요청
